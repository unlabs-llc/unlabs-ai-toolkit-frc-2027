## Re-measured against alpha-7 — 2026-09-04

A GradleRIO **`2027.0.0-alpha-7`** project (Gradle 9.4.1, JDK 25.0.4) declaring one SystemCore
target, `gradle tasks --all`:

- **22 tasks begin with `deploy`.** Every task whose name contains `deploy` also begins with it, so
  the `Bash(./gradlew deploy*)` prefix form covers the family as written.
- **Target-derived deploy tasks DO exist** once a target is declared: `deploysystemcore`,
  `deployfrcJavasystemcore`, `deployStandalonesystemcore`, and the `deployStagesystemcore*` stages
  among them. This **answers the `[verify]` below for a project that declares a target.** It does
  NOT answer it for a project generated by the normal WPILib workflow, which was not measured here;
  that question stays open.
- **No task named `simulateJava` was listed in this fixture at alpha-7.** The launcher measured here
  is **`run`**. `simulateExternalJava` also appears, but it is not a robot-program launcher — Gradle
  abbreviates the name and it exits without starting a robot program. A control keyed to the literal
  `simulateJava` matched nothing here; that is a measurement of this fixture, not a proof that no
  2027 project can register such a task.
- **Toolchain:** the classes in `wpilibj-java-2027.0.0-alpha-7` are major 69 (JDK 25); a toolchain
  pinned to Java 21 fails on them with `class file has wrong version 69.0, should be 65.0`. Every
  jar was not exhaustively checked.
- **Simulation DOES run on Linux aarch64 at alpha-7.** WPILib publishes
  `wpiutil-cpp-2027.0.0-alpha-7-linuxarm64`, and a project that declares the native and simulation
  dependencies (`nativeRelease wpi.java.deps.wpilibJniRelease(wpi.platforms.desktop)` and
  `simulationRelease wpi.sim.enableRelease()`) launches and prints
  `********** Robot program startup complete **********`. A build that declares only the Java
  dependencies fails in `RuntimeLoader` with `no wpiutiljni in java.library.path` — that is a
  MISCONFIGURED BUILD, not an unavailable platform, and an earlier draft of this note misread it as
  the latter.

The alpha-6 measurements below are retained as alpha-6 measurements and are not restated as current.

## Deploy is a task family

Read from the registration sites in source, not from a tutorial:

| Task | Registered at | Source at `Last verified` |
|---|---|---|
| `deploy` | `DeployExtension.java:154` — `project.getTasks().register("deploy", …)` | `wpilibsuite/deploy-utils@4c96861fd72e4ea3f42fda02cf8cb68f261b057c`, fetched 2026-08-06 |
| `deployStandalone` | `DeployExtension.java:162` | same |
| `deploy<TargetName>` | `RemoteTarget.java:88` — `register("deploy" + name, …)` | same |
| `deployStandalone<TargetName>` | `RemoteTarget.java:92` | same |

`<TargetName>` is the name of a deploy target created by the build. At
`wpilibsuite/GradleRIO@46bf487150b3f66ca1ef10c11445c4ca2d8235b4` (tag
`v2027.0.0-alpha-6`), `WPILibDeployPlugin.java` calls
`deployExtension.getTargets().registerFactory(SystemCore.class, …)`: that registers a factory for
constructing Systemcore targets; it does not create a target instance or choose its name. In the
single-Java-project GradleRIO 2027.0.0-alpha-6 fixture measured 2026-08-23, `./gradlew tasks --all`
listed `deploy` and `deployStandalone` but no target-derived deploy task. Whether a normally generated
team project creates a Systemcore target remains **not established** here. `[verify]`

> **Consequence for any control that guards deploying.** There is no single task name to match. A
> control keyed to the literal string `gradlew deploy` does not cover target-derived tasks that a
> build may register, and a control keyed to a fixed list does not cover a target this file has not
> seen.
>
> **Match the family, not a name.** This is why the permission deny rule is written
> `Bash(./gradlew deploy*)` with no space: the pinned deploy-utils registration sites establish the
> `deploy`-prefixed family even though the available target names are build-specific. This is a deny
> boundary, not evidence that any particular target exists in a project.

### The VS Code route is a separate entry point

From the official 2027 documentation, *Building and Deploying Robot Code*, verbatim:

> "To deploy a robot program, select **Deploy Robot Code** from any of the three locations from the
> previous instructions (or press `shift` + `f5`). That will build (if necessary) and deploy the robot
> program to Systemcore."

Source: `https://docs.wpilib.org/en/2027/docs/software/vscode-overview/deploying-robot-code.html`.

**This mattered to the withdrawn gate and would matter to any successor:** the VS Code command reaches
Systemcore through its own **entry point** — a menu item and a keybinding, not a terminal invocation.
Whether it does so by invoking the Gradle deploy tasks recorded above was **not established** from this
page, which states the outcome and not the mechanism. `[verify]` A control keyed only to a
`gradlew deploy*` invocation should not be assumed to cover this route until that is verified.

## Simulation

From the official 2027 documentation, *Robot Simulation — Introduction*, verbatim:

> "Simulation can also be run outside of VS Code using `./gradlew simulateJava` for Java or
> `./gradlew simulateNative` for C++."

Source: `https://docs.wpilib.org/en/2027/docs/software/wpilib-tools/robot-simulation/introduction.html`.

| Language | Task |
|---|---|
| Java | `simulateJava` |
| C++ | `simulateNative` |

The same page also states that the VS Code **Run** button "does not set up simulation appropriately and
should not be used" — the *WPILib: Simulate Robot Code* menu item is the supported editor route.

**A validation skill that runs a simulation stage needs authorization for the invocation it actually
runs.** Permission policy is owned by the shipped settings template; this reference does not recommend
a wildcard allow rule for simulation or any other Gradle task.

## Vendor dependencies

From the official 2027 documentation, *3rd Party Libraries*, verbatim:

> "Open a command-line instance at the project root, and enter `gradlew vendordep --url=<url>` where
> `<url>` is the vendor JSON URL. This will add the vendor library dependency JSON file to the
> `vendordeps` folder of the project."

| Location | Path |
|---|---|
| Project vendordeps | `<project>/vendordeps/` |
| System vendordeps (Unix/macOS) | `~/wpilib/2027/vendordeps/` |
| System vendordeps (Windows) | `C:\Users\Public\wpilib\2027\vendordeps\` |

The `v2027.0.0-alpha-6` release notes add, verbatim: *"It is also necessary to import vendor libraries
again, since older vendor libraries must be updated to be compatible with 2027 Alpha 5/6 projects."*

**`vendordeps/` is not the baseline's to write.** No baseline artifact creates, edits, or deletes
anything under it, and the permission template denies edits there. The scaffold's non-invasiveness
assertion checks the pre-existing `vendordeps/Vendor.json` for tracked changes; it does not detect a
new path created under `vendordeps/`. That limit matters because the moment the baseline edits a
vendordep, every toolchain upgrade becomes a merge conflict a team blames the baseline for.

## Permission boundary for these tasks

**This reference recommends no wildcard Gradle allow set.** The shipped settings template owns the
actual permission policy. Its exact allow entries deliberately make an option-bearing or additional-
task invocation prompt rather than preauthorizing a broader command line; that costs automation when
a legitimate build, test, or simulation option is needed.

The reason is established by installed-safe public sources:

- Claude Code's matcher says a single `*` spans spaces and multiple arguments
  (`https://code.claude.com/docs/en/permissions`, fetched 2026-08-23).
- Gradle permits options after task names and documents `-I` / `--init-script` as selecting an
  initialization script
  (`https://docs.gradle.org/current/userguide/command_line_interface.html`, fetched 2026-08-23).
- Gradle says attached init scripts run during initialization, before settings and project build
  scripts, and can configure projects or apply plugins
  (`https://docs.gradle.org/current/userguide/init_scripts.html`, fetched 2026-08-23).

Therefore a trailing-wildcard task rule such as `Bash(./gradlew simulateJava *)` also authorizes
`./gradlew simulateJava --init-script /tmp/x.gradle`; it is not confined to the simulation task's
ordinary behavior. This reference names that unsafe shape as a counterexample, not as a grant.

The deploy-family deny boundary above is separate. It does not make an option-bearing allow safe,
and this file does not claim that it constrains every effect an init script can cause. Neither the
permission matcher nor init-script execution was probed against a shipped Claude Code binary here;
the claims above are limited to the cited current documentation.
